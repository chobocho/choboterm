2026-10-18 — 옛 장비용 SSH 알고리즘 (서버별 허용)

  • 문제: Go SSH 기본값에 diffie-hellman-group1-sha1·group-exchange-sha1 키 교환과 aes128-cbc·3des-cbc·arcfour 암호화가 없어 오래된 스위치·공유기·임베디드 장비에 "no common algorithm"으로 접속 실패
  • 수정: 협상 실패가 옛 알고리즘으로 풀리는 경우만 sshconn.LegacyError(서버·항목·옛 알고리즘 목록)로 돌려주고, 앱이 "이 서버에 한해 허용하고 접속할까요?"를 물어 예면 서버별 servers[].legacySSH에 저장 후 다시 접속. 다음부터 바로 접속. 허용해도 안전한 알고리즘을 먼저 제시. 점프 호스트도 같은 경로(오류가 %w로 감싸져 전달)
  • Connect의 원격 접속 부분을 connectRemote로 분리(재시도용), 질문 창 공통 함수 askYesNo 사용
  • 테스트: ssh_legacy_test.go(group1-sha1 / aes128-cbc / 3des-cbc 서버: 허용 전 LegacyError, 허용 후 접속 · 옛 알고리즘으로 안 풀리는 실패(group16-sha512 전용)는 묻지 않음 · 허용해도 안전한 것 우선), app_legacy_test.go(거절 시 실패·기억 안 함, 허용 시 접속·기억, 다음엔 묻지 않음), 번역 테스트. 실제 옛 장비로는 확인하지 못함(같은 x/crypto 구현의 테스트 서버로 확인)

2026-10-18 — FTPS (FTP over TLS)

  • FTP 접속 시 로그인 전에 AUTH TLS를 먼저 요청. 서버가 지원하면 명령·데이터 연결 모두 TLS(창 제목 FTPS), 거부하거나 TLS 핸드셰이크가 인증서 확인 전에 실패하면 예전처럼 일반 FTP. 포트 990은 implicit FTPS(되돌아가지 않음). 로그인 실패는 일반 FTP로 다시 시도하지 않음(비밀번호 평문 전송 방지)
  • 시스템이 신뢰하지 않는 인증서(자체 서명·만료·이름 다름)는 이유·발급 대상·발급자·유효 기간·SHA256 지문을 보여 주고 질문(창: 메시지 상자, 브라우저: 페이지 안 질문). 신뢰하면 서버별 servers[].ftpsCert에 저장해 다시 묻지 않고, 바뀌면 경고와 함께 다시 질문. 거부하면 USER/PASS를 보내지 않음
  • 실서버(pyftpdlib TLS_FTPHandler, 스크래치 가상환경)로 확인하다 발견·수정: ① TLS 1.3에서 업로드 후 응답(226)이 오지 않아 멈춤 — 업로드 중 읽지 않은 세션 티켓 때문에 소켓을 닫을 때 RST가 나가고 서버가 응답 없이 끊음(TLS 1.2로 제한하면 통과해 원인 확인). ② 보기 창처럼 다운로드를 중간에 멈추면 같은 이유로 멈춤. → 업로드했거나 끝까지 읽지 않은 TLS 데이터 연결은 close_notify 후 서버가 닫을 때까지(최대 10초) 읽고 닫음. ③ 응답 없는 명령 중에 Close가 잠금을 기다리며 멈춤 → 잠금을 못 얻으면 제어 소켓을 바로 닫음
  • 테스트: internal/transfer/ftps_test.go(Go 가짜 FTPS 서버: explicit·implicit·자체 서명·시스템 신뢰·거부·AUTH 미지원·깨진 TLS·로그인 실패·다운로드 중단 — 중단 테스트는 수정을 끄면 15초 만에 실패), app_ftps_test.go(서버별 기억·변경 시 재질문), i18n 번역 테스트, 실서버용 TestFTPRoundTrip(CHOBOTERM_FTP_TLS)과 E2E ftps.spec.ts(E2E_FTPS 있을 때만)
  • 확인: pyftpdlib FTPS·일반 FTP 왕복(목록·업로드·다운로드·중단·이어받기·이어 올리기) 각 3회 통과, 실서버 E2E 통과, go vet·go test ./...·프런트엔드 빌드·파일 창 E2E 통과. 창(Wails)의 메시지 상자 경로는 직접 확인하지 못함

2026-10-17 — Windows 로컬 셸에서 Ctrl+V · Win+V 붙여넣기

  • 요청: cmd·WSL 탭에서 다른 Windows 앱처럼 Ctrl+V, Win+V(클립보드 기록)로 붙여넣기
  • 원인: xterm이 Ctrl+V를 ^V(0x16)로 보내고 기본 동작을 막아 paste 이벤트가 생기지 않음. Win+V도 선택한 항목을 Ctrl+V로 붙이므로 같은 문제
  • 수정(frontend/src/tabs.ts): Windows의 로컬 셸(cmd·PowerShell·WSL) 탭이 연결된 동안 Ctrl+V를 xterm에서 빼서 브라우저가 paste 이벤트를 내게 함. 기존 paste 처리기를 그대로 거쳐 여러 줄 확인 창도 동작. SSH·Telnet·시리얼 탭과 Linux에서는 이전처럼 ^V 전송(Ctrl+Shift+V는 그대로)
  • 도움말(한·영)에 "Ctrl+V · Win+V" 줄 추가
  • 보완: WSL의 vim(블록 선택)·nano(다음 페이지)·less 등 전체 화면 프로그램(대체 화면 버퍼) 안에서는 Ctrl+V를 ^V로 보냄. 그 안에서 붙여넣기는 Ctrl+Shift+V·우클릭. cmd에서 prompt $E[?1049h로 대체 화면에 들어가는 E2E 테스트 추가(보완을 끄면 실패), 전체 E2E 77개 통과
  • 확인: E2E paste.spec.ts에 회귀 테스트 추가(수정을 끄면 실패, 켜면 통과). 프런트엔드 빌드, go vet·go test ./..., E2E 76개 중 75개 통과(고양이 기지개 테스트 1개는 병렬 부하 때 간헐 실패, 단독 반복 6/6 통과 · 이번 변경과 무관)
